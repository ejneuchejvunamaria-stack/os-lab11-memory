## Задание 8
В ходе эксперимента мы запустили Docker-контейнер с ограничением памяти в 128 МБ.
В первом эксперименте программа выделяла 100 МБ. Контейнер успешно отработал, JSON-файл показал `"ExitCode": 0` и `"OOMKilled": false`.
Во втором эксперименте мы увеличили запрос до 400 МБ (для наглядности). Контейнер был принудительно завершен. JSON-файл показал `"ExitCode": 137` (что означает 128 + 9, то есть завершение сигналом SIGKILL) и `"OOMKilled": true`.

**Ответы на вопросы:**
1. **Почему программа может успешно работать на хосте, но завершаться в контейнере?**
   На хосте программа имеет доступ ко всей физической памяти компьютера (в нашем случае 4.8 ГБ), поэтому 400 МБ выделяются без проблем. В контейнере же действует жесткое ограничение (лимит 128 МБ), и как только программа пытается превысить этот порог, срабатывает механизм OOM (Out Of Memory) и убивает процесс.
2. **Каким механизмом Linux Docker ограничивает память?**
   Docker использует механизм ядра Linux под названием **cgroups** (control groups). При запуске контейнера с флагом `--memory=128m` Docker создает cgroup, в которой прописывает этот лимит для всех процессов контейнера.
3. **Создаёт ли Docker отдельное виртуальное адресное пространство для каждого процесса?**
   Нет, отдельное виртуальное адресное пространство для каждого процесса создает само ядро Linux (это фундаментальное свойство ОС). Docker лишь изолирует процессы с помощью пространств имен (namespaces) и ограничивает ресурсы (cgroups).
4. **Чем ограничение памяти контейнера отличается от размера виртуальной памяти процесса?**
   Ограничение контейнера (cgroup) ограничивает *физическую* используемую память (RSS). Размер виртуальной памяти (VSZ) процесса может быть огромным, но это лишь зарезервированные адреса, которые еще не занимают реальные физические страницы. OOM killer срабатывает именно при превышении физического лимита.
